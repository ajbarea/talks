    4 · The method

    The pass rule is written down: every test's interval must sit entirely above zero

    0 δ, smallest effect
    supported: above 0
    bounded: below δ
    inconclusive: neither

    Score: log-probability of the developer's real fix, per token.

    Each bar: one test's confidence interval for the gain: own adapter over the other group's (H1), or the other group's over Chromium's (H2).

    δ = : the smallest gain that matters, tokens about % more likely on average.

    H1 passes only if all tests are supported: organizations × 2 scores, the whole fix and the fix without names.

    Intervals are illustrative; δ is in nats per token. Above 0 and below δ counts as supported. Some tests (now Wikimedia's without-names test and H2) must also have a p-value below a calibrated cutoff.

    • δ = : one more exact fix per hundred comments, carried to the score by a planted-convention rate
    • ▶ supported ▶ bounded ▶ inconclusive
    • All H1 tests must pass, or H1 does not

    Why are there no results yet?

    A Stage 1 report is the plan, so it carries no confirmatory results. Pilot and development data sized the design. Results come in Stage 2, after the sealed test months are fetched.

    The field's reason: in psychology, one study found 96% positive results in standard papers and 44% in Registered Reports, on the first hypothesis of each paper.

    Scheel, Schijen, Lakens (2021), An Excess of Positive Results, doi:10.1177/25152459211007467. The authors note this does not prove Registered Reports reduce bias.

    What makes the study confirmatory?

    "The researcher has a fixed hypothesis (or several fixed hypotheses) and the objective of the study is to find out whether the hypothesis is supported by the facts/data."

    The hypotheses, the score, the smallest effect, the pass rule and the number of runs are all fixed in the report, before the sealed test months are fetched.

    Back to the questions

    Why code review data?

    House style is what reviewers enforce and rarely write down, and a review pairs a comment with the code that answered it. That pairing is the training example.

    The revision that followed the comment is a label a person produced, and the data is public for these hosts, so what leaks can be checked against known origins.

    Back to the questions

    How does this relate to InteFL?

    The Registered Report has no federated learning in it: centralized measurement, one adapter per project group, and no aggregation. The repository also holds early federated code for later steps, and no result from it is claimed here.

    InteFL is the lab's federated framework. Its aggregation and attack work becomes relevant at step two, once there is an adapter to federate.

    Which FL stack step two runs on is decided when it starts.

    Back to the questions

    What is a LoRA adapter?

    A small add-on, trained beside a frozen base model, in low-rank adaptation. The study trains one per project group at rank on .

    It is the unit a federated step would average: small, trainable at each company, and the part that would be shared instead of raw data.
