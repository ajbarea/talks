Why you should care

Your reviewers keep repeating rules no AI assistant has seen. Lessons like these teach those rules; my study tests whether an assistant learns them without your code leaving.

Here's what I did. I built an open-source tool that turns public code review into checked lessons, and with it two datasets: lessons from OpenStack and from Wikimedia. Each lesson is a reviewer's comment, the code it was about, and the code the developer wrote next. Here's why you should care. If you write code on a team, your reviewers keep repeating rules that no AI assistant has ever seen. Lessons like these are what would teach it those rules, and my study tests whether it can learn them without your code ever leaving. Let me start with one of those rules.

1 · The problem

The data that would teach them is data no company wants to share

Today the choice is all or nothing: share everything, or share nothing.

Every accepted, fixed or rejected suggestion is a training example. Pooled across companies, they would teach every assistant more, since much good practice carries over. But each company's code, and how its team works, would leave the building. So today it's all or nothing.
2 · The idea

Four research fields meet in this work

Learning together, apart

Many owners train one model; each owner's data stays home.

Small add-ons

A small add-on teaches a large model a new skill; the model stays as it was.

Learning from code review

Public code review shows the rules teams really enforce.

Testing what a model gives away

Attacks test what a trained model reveals about its training data.

Field terms, in order: federated learning; LoRA adapters; mining software repositories; inference attacks.

This work sits where four research fields meet, so here they are in a sentence each. First, learning together, apart: many owners train one model, each owner's data stays home, and only changes to the model travel. Second, small add-ons: instead of retraining a large model, you train a small add-on beside it, and the model itself stays as it was. Third, learning from code review: the public record of how teams review code shows the rules they really enforce. Fourth, testing what a model gives away: attacks that ask what a trained model reveals about its data. My idea puts all four together.
2 · The idea

My idea: a shared add-on, a private add-on, and the company decides

The company marks which of its repositories may feed the shared add-on, and only those do.

Field terms: the add-ons are LoRA adapters; training them together this way is federated learning. Repository names are illustrative.

My idea: every company runs the same frozen, open-weight base model with two small add-ons. The blue one is shared: only each company's changes to it go to a server that averages them, so code never travels. The orange one is private and never leaves. Before training, the company lists which repositories may feed the shared add-on; the rest teach only the private one, and anyone can audit the list.

4 · What's built

Every step up to the sealed test is built

Solid: built; dashed: planned. Field terms: the add-on is a LoRA adapter (rank ); the score is mean log-probability per token.

Here's the whole method. The tool collects public code review by each host's rules drops names, and replaces each account with a salted pseudonym in everything it builds. It pairs each reviewer comment and its code with the code the developer wrote next: one lesson, its label never guessed. It drops bots and one-click approvals, removes copies, and splits by month, with the test months sealed. Then it runs the study. It splits a community's projects in two, trains one small add-on per half on the same frozen model, and scores how likely each add-on finds the code the developer actually wrote. The gain is the own half's add-on against the other half's, averaged over many splits. The dashed row comes next: the sealed test, where every community must gain, then the shared and private add-ons, and the attacks on them.

What is the federation, concretely?

Clients are the parties holding review histories. Each trains LoRA adapters on a frozen shared base model; only adapter weights move, never code and never gradients over raw examples.

A round is: the server broadcasts the shared adapter, each client trains locally, each uploads only the adapter its provenance rule marks shareable, the server aggregates and rebroadcasts.

What is not federated: the private adapter, which never leaves, and the provenance rule itself, which the organization sets and audits locally.

Back to the questions

What if companies use different or closed models?

The add-ons need a base model whose weights every party can run and train against, so the federation is for companies that host an open-weight model. A company that buys a closed model by the token cannot carry the shared add-on.

Its route is the written one: a rules file or instructions the closed model reads. The study measures that route beside the adapters, in the rules-file slides.

Back to the questions

What guarantee can be offered about leakage?

None yet, and saying otherwise would be the mistake this work exists to correct.

What exists is a measurement: given a boundary, does the part that crosses it still identify its source? The published boundaries go through it.

A guarantee needs a mechanism with a proof, and the candidates are secure aggregation and differential privacy. Both are measured here rather than assumed.

Back to the questions

What are the pre-registered test and the privacy attacks?

The test: does an add-on trained on an organization's own reviews beat one trained on a sibling slice of the same organization, on months the model has not seen? It passes only if that holds in every organization tested. The rule and the sealed test months were fixed before any test result existed.

The attacks: does the shared part still reveal its source?

  • Source attribution: which organization did this add-on come from?
  • Min-loss attack: assign an example to the source whose add-on fits it best (the baseline).
  • Aggregate attack: read the combined update, not one organization's.
  • Gradient disaggregation: undo secure aggregation.

A measurement, not a guarantee.

Is the data sound?

Labels are not inferred. An example is a code hunk, the reviewer comments anchored to it, and the author's next revision, taken directly from the review server.

  • Author comments are excluded, so the signal is a reviewer's, not a self-edit.
  • Near-duplicates are removed before the split; leftover overlap is reported.
  • Label quality is audited blind, by model raters and a human. On OpenStack's audited lessons, about have a rewrite that answers its comment; the rest stay in and are scored in every arm, so they dilute a difference rather than favour one side.
  • Every filtering rule and what it removed is published: ajbarea.github.io/sphragis/dataset
  • Contamination rests on provenance: every month of data starts after the model's weights were uploaded. About of development fixes were already in their project's code then; leaving them out changes neither OpenStack's nor Wikimedia's readingchanges a reading. Dropping AI-assisted commits (by trailer) moves OpenStack's estimate by .
  • Identities are pseudonymised in everything derived from the raw data, and addresses are swept from comment text. The raw snapshots still hold some host account numbers; nothing derived does.

Back to the questions

Does public code review stand in for a private team's?

It is the only review history anyone can study openly, so every claim here is scoped to public communities. Many of their contributors are company and foundation engineers working under required review, which makes them the closest public stand-in.

Whether private teams hold their conventions the same way is untested, and no company publishes how much of its practice stays private. The federation is how that data would be used without anyone having to share it.

Back to the questions

Aren't conventions really the reviewers', and don't they change?

Partly, and the study checks it. Nearly every test example shares a reviewer with the other half of its own organization and none with a foreign one, so a reviewer effect would show up as the organization's advantage over a foreign one. An analysis planned before the test months open asks whether that advantage grows with how much of the training data the example's own reviewers wrote. Review is concentrated: in OpenStack, Wikimedia and Qt alike, the busiest tenth of reviewers are credited with about half the training examples.

People also come and go. The test months come after the training months, so conventions that changed with the people count against the result rather than for it.

Back to the questions

How does aggregation work across different adapters?

An update is stored as two small matrices whose product is the real change. Averaging the two separately and multiplying afterwards gives a different answer, so the server has to combine the products.

Clients may also hold different ranks. Existing work covers both: exact aggregation of the product, and rank-heterogeneous averaging.

That choice is a design item with a stated criterion, not an open question, and it is the one place this work picks from the field rather than adding to it.

Back to the questions

Is the dataset useful beyond this one model?

Yes. An example is a reviewer's comment, the code it was about, and the developer's real next revision. Nothing in it comes from a model, so any model or agent can be trained on it or scored against it.

The communities span several languages: OpenStack's examples are led by Python, Wikimedia's by PHP and JavaScript, and the two GitHub members, Apache and .NET, add Java, C# and more.

Would a different model do better?

More models buy generality, not a better answer: the question is whether a team's habits can be learned at all, and a model that may have read the test code cannot settle that. A second family checks the result is not a Qwen quirk.

Compressing the base model to 4 bits (QLoRA) saves memory and at best matches quality, so the main test does not use it. It is planned for the privacy half, because the deployment being tested uses it.

Back to the questions

Why not just write the rules in a file, like AGENTS.md?

That is how coding agents take conventions today: rules files (AGENTS.md, CLAUDE.md, Cursor rules), organization instructions and memory. They hold what someone wrote down.

What no one has measured is whether they capture a team's conventions. A 2026 study found developer-written context files helped agents slightly (not significantly), generated ones did not, and both cost about a fifth more inference (Gloaguen et al., arXiv:2602.11988); it does not ask whether the code follows the team's habits.

So the study adds a rules-file arm beside the adapters: the base model given the organization's written conventions, or a file distilled from each half's review comments, scored on own, sibling and foreign code by exact match, the study's secondary measure. Qwen3.6-27B distils it, since the 7B model invented rules and citations; a rule must cite two or more comments and share most of its words with one.

Back to the questions

How is this different from other shared-and-private agent work?

Splitting what agents learn into shared and private parts is no longer new. Federated Agent Optimization (Yang et al., arXiv:2610.01195) defines the field; FedWorld (arXiv:2608.01561) sorts rules into shared, cluster and private by the evidence clients give for and against them; ShareMem and FederatedSkill split memories and skills by an LLM's judgment.

Each decides the split by evidence on a server or an LLM's judgment, not by the owner declaring it from where each example came from. Three things here are not done elsewhere:

  • The owner declares the boundary before training, by where each example came from, and that declaration decides which examples may teach the shared part.
  • Tacit review conventions are what is learned, with a pre-registered test of whether the organization is where learning stops transferring.
  • The shared part is audited by attribution: can someone tell which organization it came from?

Back to the questions

Could it train an agent that checks another agent?

In principle, yes, and it is a later use rather than this study. The label audit already grades whether a developer's revision answers the reviewer's comment (answers it, partly, not at all, or needs more context). That is the judgment a checking agent would make about a coding agent's change before a human sees it.

Back to the questions

Is the tool only for code review?

Collection, pseudonymisation and the sealed time split work for any review system the tool has a route into (Gerrit and GitHub today). Pairing a comment with the change that answered it, and the cleaning rules, are specific to code review, because the research question is.
